## Positioning

**Confirmed repository fact:** KeyCourier is a native macOS app with an iPhone companion that lets AI coding tools use approved credentials without seeing their values. Codex, Claude Code and OpenCode ask for a saved credential and destination. You approve the request on your Mac or, for credentials you explicitly allow, through the paired iPhone or Telegram. KeyCourier installs the credential directly and returns a content-free receipt.

**Recommendation:** KeyCourier-OpenCore is for the owner, approved collaborators and future maintainers who need to understand and operate this repository safely. It should be positioned around its narrowest proven job, with repository-backed boundaries made as visible as its benefits.

## Differentiation and objections

- Lead with a narrow workflow and authority boundary, not generic claims such as easy, smart, secure or all-in-one.
- Compare against the user's current workaround before naming competitors.
- Treat missing release proof, platform coverage, integrations and outcome data as objections to answer honestly.

## Metadata recommendation

No marketplace title, subtitle or keyword change is recommended. If this repository becomes intentionally public, first validate the audience and evidence boundary, then consider a concise GitHub description and up to 20 relevant lowercase topics. Topic names are public even on private repositories.

## SEO, content and distribution opportunities

- Keep the GitHub description and README first paragraph aligned with the bounded repository purpose.
- Add public topics or a public explainer only after deciding that the repository should be discoverable.
- Prefer a technical case study, architecture note or operator guide over product-style demand generation.
- If a future product option emerges, validate one named audience and repeated problem before creating launch copy.

### Query themes to validate

- The primary job expressed in the audience's language
- The current workaround plus its most costly failure mode
- A privacy, evidence, offline, approval or recovery differentiator that the repository can prove
- The product or repository name only after non-branded intent is covered

Google gives no indexing or ranking guarantee. Search recommendations should be measured through impressions, clicks, click-through rate and qualified conversion, not assumed traffic.

## Conversion path and launch gates

No standalone commercial launch is recommended. A future public option must first pass these gates:

1. Confirm the repository's authority, privacy and maintenance boundaries.
2. Name one external audience and repeated problem supported by evidence.
3. Decide whether the useful output is documentation, open source, a case study or a separate product.
4. Obtain owner review before changing visibility, topics, public copy or distribution.
5. Keep this repository non-commercial if those gates do not produce a credible reason to proceed.

## Measurement

| Area | Useful measure | Guardrail |

| Findability | Maintainer can locate the authority and key runbook quickly | Do not optimise for public reach |

## Claim guardrails

- Do not invent a customer segment or revenue model.
- Do not expose private operations, personal data, customer material or credentials.
- Only publicise capabilities that current repository evidence supports.
- Label roadmap, beta, recommendation and hypothesis language explicitly.
- Avoid best, leading, guaranteed, secure, compliant, effortless and similar unbounded claims.
- Revalidate every platform-policy statement and live URL immediately before publication.
